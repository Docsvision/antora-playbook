= Сервис обслуживания ЭП

Данный раздел описывает работу Сервис обслуживания ЭП и Криптосервиса, отличия и функциональные возможности двух сервисов в системе {dv} 6 ({pl} 6.1 и выше + {wc} 18 и выше).

[#functions]
== Функциональные возможности сервисов

WARNING: Сервис обслуживания ЭП -- расширение, входящее в стандартную поставку модуля {bo}, не следует путать его с Криптосервисом. Криптосервис поставляется и настраивается отдельно.

.Назначение сервиса обслуживания ЭП:
* Если срок действия сертификата не истёк, Сервис обслуживания ЭП указывает в журнале подписей {wc}а актуальный статус подписи, её тип и дату окончания срока действия сертификата, даёт возможность просматривать дополнительную информацию о подписи в xref:webclient:user:docs-sign.adoc#advanced-info[журнале подписей {wc}а].
* Функциональность Сервиса обслуживания ЭП может быть дополнена отдельным компонентом -- Криптосервисом.

.Криптосервис дополняет функции сервиса по обслуживанию следующими возможностями:
* Если сервер {dv} работает под управлением Linux:
** Криптосервис используется для формирования и проверки подписей, включая подписи с нестандартными для .NET алгоритмами в сертификатах, например, с сертификатами КриптоПро.
** Криптосервис указывает в xref:webclient:user:docs-sign.adoc#advanced-info[журнале подписей {wc}а] актуальный статус подписи, её тип и дату окончания срока действия сертификата, делает доступной расширенную информацию о подписи.
** Криптосервис улучшает подпись до CAdES-A.
* Если сервер {dv} работает под управлением Windows:
** {blank}
+
Проверка и формирование подписи не требуют криптосервис и соответствующие лицензии, но в таком случае xref:6.1@webclient:user:docs-sign.adoc#advanced-info[отображение штампа времени] и улучшение подписи до CAdES-A будет недоступно.

[#requirements]
== Требования для использования Криптосервиса

.Для использования криптосервиса потребуется:
* Модуль Служба {ws} {ws-req} и выше.
* https://www.docker.com/[Docker] актуальной версии, если криптосервис планируется разворачивать в контейнере. Криптосервис может быть получен из общего реестра образов Docker Hub -- `docsvision/cryptoservice` или реестра образов {dv} -- `packages.docsvision.com/cryptoservice`.
* Опция лицензии {dv} _Сервис обслуживания электронной подписи_ (только для добавления архивного штампа времени).
* Из-за использования библиотеки tspcom.dll Криптосервис требует быть развернут минимум в 32-битном процессе Службы рабочих процессов.
* [[jcsp]]Сборки, входящие в состав https://cryptopro.ru/products/csp/downloads#latest_csp50r3_jcsp[Java CSP] версии {jcsp-v}, и лицензия на право использования ПО "КриптоПро Java CSP" на одном сервере.
* Лицензия на право использования СКЗИ "КриптоПро CSP" версии {csp-v} на сервере.
// Для формирования подписи лицензия не требуется, см. требования GBL-3116, GBL-3074, GBL-3326 и GBL-2865

[#cryptoservice]
== Криптосервис в {dv} 6.1 Linux

. Получите сборки КриптоПро Java CSP <<jcsp,необходимой версии>> и поместите их в локальный каталог хоста `./java-csp-5.0.45559-A-b34f3a2f`.
. Смонтируйте эту папку в каталог Docker-контейнера `/app/BOOT-INF/lib/java-csp` и запустите контейнер:
+
[source]
----
docker run -d -p 8094:8094 -v ./java-csp-5.0.45559-A-b34f3a2f:/app/BOOT-INF/lib/java-csp packages.docsvision.com/cryptoservice
 <.>
----
<.> Если используется Docker Hub, замените `packages.docsvision.com/cryptoservice` на `docsvision/cryptoservice`.
+
При запуске контейнера всё содержимое папки будет импортировано в хранилище.
+
Настройки криптосервиса задаются в командной строке. При запуске контейнера необходимо связать порт хоста с портом контейнера, например, `-p 8100:8094`. В примере `8100` -- порт хоста, `8094` -- порт контейнера. Для работы функций проверки и формирования подписи сервер {dv} должен подключаться к контейнеру через порт хоста. Адрес Криптосервиса указывается в конфигурационном файле, <<config,см. подробности ниже>>.

По умолчанию Криптосервис использует TSP-службу с адресом `http://cryptopro.ru/tsp/tsp.srf`. При необходимости адрес используемой TSP-службы можно переопределить с помощью переменной окружения `TSP_SERVICE_ADDRESS`. Ниже приведён пример переопределения адреса TSP-сервиса:

 $ docker run -d -p 8100:8094 -e TSP_SERVICE_ADDRESS=http://testca2012.cryptopro.ru/tsp/tsp.srf packages.docsvision.com/cryptoservice

Контейнер поставляется в комплекте со следующими сертификатами:

* https://www.gosuslugi.ru/crt[Защищённые сертификаты Минцифры].
* https://ca.kontur.ru/about/certificates[Сертификаты УЦ "Контур"].
* https://tlsca.cryptopro.ru/UI/CaCerts.aspx[Сертификаты "Крипто-Про УЦ 2.0" (TLS CA)].
* http://cpca20.cryptopro.ru/[Сертификаты УЦ ООО "Крипто-Про"].

При необходимости использования дополнительных сертификатов выполните одну из следующих настроек:

* Укажите путь к папке сертификатов:
. Смонтируйте сертификаты и сборки КриптоПро Java CSP <<jcsp,необходимой версии>> в соответствующие каталоги Docker-контейнера и запустите контейнер:
+
[source,bash]
----
docker run -d -p 8094:8094 -v ./java-csp-5.0.45559-A-b34f3a2f:/app/BOOT-INF/lib/java-csp -v ./Cert:/var/cryptoservice/cacerts packages.docsvision.com/cryptoservice <.>
----
<.> Если используется Docker Hub, замените `packages.docsvision.com/cryptoservice` на `docsvision/cryptoservice`.
+
При запуске контейнера всё содержимое папки будет импортировано в хранилище.
+
* Заново соберите образ:
+
. Создайте Dockerfile. Если используется Docker Hub, замените `packages.docsvision.com/cryptoservice` на `docsvision/cryptoservice`:
+
[source,dockerfile]
----
FROM packages.docsvision.com/cryptoservice

COPY ./java-csp-5.0.45559-A-b34f3a2f/ /app/BOOT-INF/lib/java-csp/ <.>
COPY ./your/cacerts/ /var/cryptoservice/cacerts/ <.>
----
<.> Смонтируйте сборки КриптоПро Java CSP <<jcsp,необходимой версии>>.
<.> Смонтируйте сертификаты.
+
. Соберите собственный образ:
+
 $ docker build . -t cryptoservice
+
. Запустите контейнер:
+
 $ docker run -d -p 8100:8094 cryptoservice

[#ocsp]
== Улучшение подписи с сертификатом без адреса OCSP сервиса

При улучшении подписи, созданной с помощью сертификата без адреса OCSP сервиса, могут возникать ошибки вида: `The signer certificate <...> must have OCSP evidence but it doesn't contain any OCSP reference. OCSP evidence is not created`.

Исправить ситуацию можно, если известен адрес OCSP сервиса, выдавшего сертификат.

.Требования к сертификату:
****
* Сертификат, которым выполнялась подпись, должен быть доверенным. Доверенный сертификат -- это сертификат, у которого корневой и промежуточные сертификаты добавлены в доверенные в образе Крипто-сервиса.
* Сертификат OCSP сервиса (для подписания ответов сервиса) должен быть доверенным. Сертификат с большой вероятностью будет недоверенным в случае, если используется неквалифицированная электронная подпись (НЭП).
* Сертификат OCSP сервиса должен быть выпущен тем же УЦ, что и сертификат, которым выполнялась подпись (поле `Issuer` в сертификатах должно совпадать). Иными словами, нужно использовать OCSP сервис того же УЦ, который выпустил сертификат, которым выполнялась подпись. Только данный УЦ может контролировать статус отзыва сертификата.
* Сертификат OCSP сервиса можно уточнить в УЦ.
* Сертификат TSP сервиса также должен быть доверенным.
* Получить сертификат TSP сервиса можно также через техподдержку компании, которая предоставляет сервис, либо через утилиту CryptExpert.
****

Когда адрес сервиса известен, необходимо в файле настроек криптосервиса `/etc/cryptoservice/settings.json` указать актуальные адреса OCSP серверов следующим образом:

[source,json]
----
{
    "ocspSettings": [
        {
            "ocspUrl": "http://ocsp-service.ru/ocspn/ocsp.srf", <.>
            "serial": "17192b01038046a1649b8a076964699c4" <.>
        },
        {
            "ocspUrl": "http://ocsp-service.example.ru/ocspn1000000/ocsp.srf",
            "serial": "1f409aa452fd10ee11500ea83ca0f3ce2"
        }
    ]
}
----
<.> `"ocspUrl"` -- адрес OCSP сервиса.
<.> `"serial"` -- серийный номер корневого сертификата улучшаемой подписи.

Конфигурационный файл `settings.json` должен располагаться в контейнере криптосервиса по пути `/etc/cryptoservice/`. Если в файле задана хотя бы одна группа настроек `ocspSettings`, то при улучшении подписи криптосервис будет проверять цепочку родительских сертификатов сертификата улучшаемой подписи.

Серийные номера сертификатов сопоставляются с номером, указанным в конфигурационном файле, при совпадении заданный адрес OCSP будет использоваться для самого близкого родительского сертификата. Чтобы серийный номер сертификата считывался успешно, поместите его в каталог корневых сертификатов `/var/cryptoservice/cacerts`.

Контейнер криптосервиса можно сразу смонтировать вместе с файлом настроек OCSP сервиса следующим образом:

 $ docker run -d -p 8100:8094 -v /path/to/settings.json:/etc/cryptoservice/settings.json packages.docsvision.com/cryptoservice


[#https]
== Настройка подключения к криптосервису по HTTPS

. Создайте PKCS12-файл (`.p12` или `.pfx`) предпочтительным способом. Шаг можно пропустить, если уже есть сертификат в формате `.p12` или `.pfx`. Ниже приведён пример генерации файла при помощи утилиты OpenSSL.
+
Для создания PKCS12-файла потребуются файлы `fullchain.pem` и `privkey.pem`, которые можно получить из полученного в УЦ сертификата. Также можно сгенерировать самоподписанный сертификат, см. подробнее: "xref:https-connection.adoc#certificate[Создание самоподписанного сертификата]".
+
[source,bash]
----
openssl pkcs12 -export \
-in fullchain.pem \ <.>
-inkey privkey.pem \ <.>
-out keystore.p12 \ <.>
-passout pass:MyP@ssw0rd <.>
----
<.> Промежуточный и конечный сертификат
<.> Приватный ключ
<.> Имя выходного PKCS12-файла
<.> Пароль для защиты PKCS12-файла
+
. Создайте файл конфигурации.
+
[source,bash]
----
cat > application.properties <<EOF
server.ssl.key-store=/keystore.p12 <.>
server.ssl.key-store-password=MyP@ssw0rd <.>
server.ssl.keyStoreType=PKCS12
EOF
----
<.> Путь до PKCS12-файла в контейнере
<.> Пароль от PKCS12-файла
+
. Запустите криптосервис:
+
[source,bash]
----
docker run -d -p 8100:8094 \
-v $(realpath application.properties):/application.properties \ <.>
-v $(realpath keystore.p12):/keystore.p12 \ <.>
packages.docsvision.com/cryptoservice \
java org.springframework.boot.loader.JarLauncher \
--spring.config.additional-location=/application.properties <.>
----
<.> Монтирование файла конфигурации `хост:контейнер`
<.> Монтирование PKCS12-файла `хост:контейнер`
<.> Путь до файла конфигурации в контейнере
